# VLM 接入与评测计划（更新版）

> 目标：在现有“LLM 元规划 + 代码执行”的框架上加入 **VLM 视觉感知**，用“AI 生成图片”模拟相机输入；同时保持 **可插拔**，方便替换/对比不同 VLM，并评测两种组合策略：  
> ① 只在元规划阶段用 VLM；② 元规划 + 每次执行循环都用 VLM。

## 0. 先统一术语与边界（务必先做）
- [ ] 明确输入：单张图片 or 多视角图片（建议先单张，后扩展多视角）。
- [ ] 明确输出：VLM 只负责“感知→结构化状态”，不直接输出动作代码。
- [ ] 明确可控变量：同一套图片/任务/提示词/温度/随机种子，用于公平对比。
- [ ] 明确不做：不接真实仿真器；不要求真实物理精度，只追求可复现评测。

## 1. 设计可扩展的 VLM 插件接口（框架层）
### 1.1 统一“感知结果”数据结构（建议 JSON）
- [ ] 定义 `SceneObservation`（建议字段）：
  - [ ] `image_id` / `timestamp`
  - [ ] `objects`: `[{name, bbox?, position?, attributes?, confidence}]`
  - [ ] `relations`: `[{subj, rel, obj, confidence}]`（如 `in/near/on/left_of`）
  - [ ] `robot_state?`（如手里拿着什么：可选，先从环境状态提供）
  - [ ] `raw_text`（VLM 原始输出，便于追溯）
- [ ] 定义“坐标约定”：如果暂时不做精确定位，可用离散区域（如 `table_area/stairs_area`）。

### 1.2 统一 VLM 适配器接口（可插拔）
- [ ] 新增抽象类/协议：`VLMAdapter`
  - [ ] `predict(image, prompt, context) -> SceneObservation`
  - [ ] `name`, `version`, `supports_multiview`, `supports_bbox` 等元信息
- [ ] 支持最小可用的 2 个实现：
  - [ ] `MockVLMAdapter`：直接读“标注真值”，用于联调与上限对照
  - [ ] `LLMAsVLMAdapter`（临时替代）：把图片描述当作文本输入（用于无 VLM 时先跑通链路）
- [ ] 设计配置方式（建议 `config.yaml` 或环境变量）：
  - [ ] `VLM_PROVIDER=mock/openai/xxx`
  - [ ] `VLM_MODE=meta_only | meta_and_step`
  - [ ] `USE_VLM_CACHE=true/false`

### 1.3 日志与缓存（为了评测必须做）
- [ ] 统一落盘日志（建议 JSONL）：
  - [ ] 每次感知调用：输入 `image_id`、输出 `SceneObservation`、耗时、tokens/cost（如可得）
  - [ ] 每次规划：输入（指令+观测）、输出 plan、耗时
  - [ ] 每次执行循环：子任务、生成代码、执行结果、是否满足退出条件
- [ ] 对 VLM 和 LLM 都加缓存键（包含 model、prompt、image_id、context）。

## 2. 用图片模拟“环境感知”的数据集（评测基石）
### 2.1 组织一个最小基准集（先小后大）
- [ ] 建一个目录（建议）：`data/images/`、`data/annotations/`、`data/tasks/`
- [ ] 先做 **20–50 张**图片的 MVP（覆盖楼层、物体、遮挡、相似物体等）
- [ ] 每张图配一份标注（建议 JSON）：
  - [ ] 物体类别（如 `red doll`, `basket`）
  - [ ] 可选 bbox/区域（先区域也行）
  - [ ] 关键关系（如 `red doll in basket`）

### 2.2 任务集（用于端到端）
- [ ] 定义 10–30 条任务指令（中英皆可，但建议统一语言）
- [ ] 每条任务绑定：
  - [ ] 初始图（或图序列）
  - [ ] 期望终态（例如“手为空且娃娃在筐里”）
  - [ ] 可选：允许的中间步骤/容错规则

## 3. 两种 VLM 组合策略的落地方案
### 3.1 策略 A：只在“元规划”阶段用 VLM（Meta Only）
- [ ] 在 `generate_plan()` 前调用 VLM，得到 `SceneObservation`
- [ ] 把 `SceneObservation`（结构化+可选自然语言摘要）注入元规划 prompt
- [ ] 执行阶段仍使用现有 mock 环境的 `get_observation_*`（或直接用环境状态）
- [ ] 评测关注：VLM 是否改善“拆解质量/子任务顺序/退出条件可判定性”

### 3.2 策略 B：元规划 + 每次执行循环都用 VLM（Meta + Step）
- [ ] 每次 while 循环开头先“看一眼”：VLM(image)->SceneObservation
- [ ] 用 VLM 观测来做两件事：
  - [ ] 条件检查：把 `SceneObservation` 转成 `observation_description` 给 `ConditionCheckerLMP`
  - [ ] 子任务执行：把可见物体列表/关系传给执行器（替代 `get_observation_objects()`）
- [ ] 评测关注：闭环鲁棒性（错误感知是否导致错误动作/循环卡死）、额外成本与延迟

## 4. VLM 性能怎么测：分两层评测（推荐）
### 4.1 感知层（VLM 自身能力）
- [ ] **对象识别**：precision / recall / F1（按类别）
- [ ] **关系识别**：relation accuracy / F1（如 in/on/near）
- [ ] **定位能力（可选）**：区域分类准确率或 bbox IoU（若有 bbox）
- [ ] **稳定性**：同图多次调用一致性（temperature=0 时应高度一致）
- [ ] **成本与时延**：平均耗时、tokens、失败率（超时/解析失败）

### 4.2 端到端任务层（系统最终表现）
- [ ] **任务成功率**：是否达成最终条件（例如“娃娃在筐里且手为空”）
- [ ] **子任务效率**：平均循环次数、平均动作数
- [ ] **错误类型统计**（建议强制分类）：
  - [ ] 误检/漏检导致的错误动作
  - [ ] 规划错误（子任务缺失/顺序错/退出条件不可判定）
  - [ ] 执行错误（走错、拿不到、drop 失败等）
- [ ] **策略对比**：同一 VLM 在 A/B 两策略下的成功率、成本、时延曲线

## 5. 时间安排（可按 4–6 周滚动迭代）
### 第 1 周：把“接口 + 数据 + 日志”打地基（可跑通）
- [ ] 输出 `SceneObservation` schema（先用区域，不追求精确坐标）
- [ ] 写 `VLMAdapter` 抽象与 `MockVLMAdapter`
- [ ] 建 `data/images/` + 20 张图 + 对应标注
- [ ] 打通“读取图片→VLM→SceneObservation→序列化日志（JSONL）”
- [ ] 增加配置开关：`VLM_MODE=meta_only`

### 第 2 周：接入策略 A（元规划用 VLM）并做第一轮评测
- [ ] 元规划 prompt 增加“视觉观测摘要”段落
- [ ] 设计“观测摘要器”（把结构化观测压缩成稳定文本）
- [ ] 跑通 10 条任务，生成基线日志
- [ ] 输出第一版评测脚本：感知层 + 任务层（最少成功率/耗时）

### 第 3 周：接入策略 B（每步执行都用 VLM）并做对比
- [ ] 执行循环里引入 VLM 感知（含缓存）
- [ ] 条件检查改为读 VLM 观测（而不是 mock env 的文本观测）
- [ ] 执行器改为读 VLM 可见物体/关系（而不是环境真值）
- [ ] 加“防卡死”策略：最大循环次数、失败重试、低置信度降级（例如回退到环境真值/提示澄清）

### 第 4 周：扩展数据集与指标，形成可复现实验套件
- [ ] 图片扩展到 50–200 张（分难度：easy/medium/hard）
- [ ] 任务扩展到 30+ 条（覆盖：寻找/上楼/放置/多物体）
- [ ] 增加更细指标：关系 F1、错误类型统计、每任务成本
- [ ] 固化“实验配置文件”：一键跑多 VLM、多策略，产出对比表格（CSV/Markdown）

### 可选第 5–6 周：开始真正接入候选 VLM
- [ ] 为每个候选 VLM 写一个 Adapter（只实现 `predict`，其余复用）
- [ ] 做统一提示词模板（便于跨模型对齐）
- [ ] 输出对比报告：不同 VLM × 两策略的雷达图/表格（成功率、成本、时延、鲁棒性）

## 6. 你需要尽早拍板的 5 个关键选择（不然会拖慢）
- [ ] 图片里物体类别列表（建议 10–20 类先固定）
- [ ] 定位表述：bbox vs 区域（建议先区域）
- [ ] 关系集合：`in/on/near/left_of/right_of`（建议先 2–3 个）
- [ ] 任务语言：中文 or 英文（建议统一）
- [ ] 评测“成功”的判定方式（建议用结构化终态条件，不要只靠自然语言）
